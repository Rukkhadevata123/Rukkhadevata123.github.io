    导读：技术分歧怎样变成身份冲突 #

    假设有人批评 Snap 闭源。你指出，snapd 按 GPLv3 发布，Snap Store 的服务端闭源。对方说：“我说得不准确，我真正反感的是 Store。”他依然反感 Snap 的分发方式，但你们已经弄清了争议在哪儿，可以接着谈商店由谁控制，以及这对用户有什么影响。

    同样一句澄清，也可能换来另一种回应：“你不过是 Canonical 的维护者。”这时，如果你开始解释自己跟 Canonical 有什么关系，两个人很可能谈上半天，都没再碰到商店到底开放了什么这个问题。

    我关心的是讨论从哪一步开始换了话题。查清技术事实，有时能消除误解，有时能让双方更明白为什么各自坚持原来的选择。更难判断的是，什么时候值得继续举证，什么时候对方已经在评判你的身份，以及为什么几次这样的交锋就足以影响我们对整个社区的印象。

    1 不同的目标与约束：为什么会选出相反的方案 #

    1.1 先分清是在比较事实，还是做选择 #

    “macOS 与 Windows 的 HDR 色彩管理和显示链路有什么差异”，问的是技术属性，需要靠文档、实现和测试回答。“哪套系统更适合自己的 HDR 工作流”，问的是选择，还要考虑软件兼容性、使用习惯和维护成本。一个人可以不在意 HDR，但两个系统的实现差异仍然存在。

    这两类问题经常出现在同一段对话里。“我不会用这个平台”说明了一项选择，却没有回答它的 HDR 实现有什么特点。如果讨论从技术差异转到个人选型，就需要把用途和条件补上，才能知道双方的结论是否真的冲突。

    “Arch 和 Ubuntu 哪个更好”也常常是在问怎么选。给家人装一台以后要靠自己远程维护的电脑，我会考虑升级后出了问题该怎么处理。给自己的开发机选系统，我愿意花在维护上的时间可能就不一样。

    1.2 一个技术对象包含哪些属性 #

    讨论一种技术时，我们往往在同时评价兼容性、启动时间、控制权和维护成本。可以把这些属性记作一组量：

    \[ \mathbf v(x) = (\text{兼容性},\ \text{启动时间},\ \text{磁盘占用},\ \text{控制权},\ \text{维护成本},\ \text{更新速度},\ \text{隔离性},\ \text{生态规模},\ \dots) \]

    这里的 \(x\) 是被比较的方案，\(\mathbf v(x)\) 是它的属性向量，也就是这份可以逐项展开的属性清单。不同属性可能需要不同的测量方法，其中一些还依赖使用条件。

    我在 Windows 上的体验就有这种区别：Unreal Engine 的工具链、Windows Terminal、PowerToys 都是好用的，同一系统里某些 UI 决策和某些硬件上的睡眠唤醒体验则很差。这些判断针对不同属性，可以同时成立。

    把评价写到这一步，读者就能继续追问具体依据。如果只留下“好”或“差”一个总评，哪些表现支持了这个结论、哪些代价被接受了，都会变得不清楚。

    1.3 相同的属性，怎样形成不同的排序 #

    一个人可能把软件新鲜度看得很重，并愿意承担较多维护工作；另一个人希望升级后的行为可预测，愿意接受较旧的软件版本。即使两人认可同一组数据，他们也可能分别选择 Arch 和 Debian。

    这里可以区分两个量：\(\hat{\mathbf v}_i(x)\) 表示第 \(i\) 个人对方案属性的认识，\(\mathbf w_i\) 表示他对各项属性的重视程度。用一个简化的加权式表示个人评价：

    \[ U_i(x) = \mathbf w_i^\top \hat{\mathbf v}_i(x) \]

    这个式子把“我认为它表现怎样”和“我有多在意这种表现”分开了。属性值需要先约定可比较的尺度和方向，再按权重形成评分；分数相同的方案可以并列。现实选择还会涉及阈值和属性交互，本文只借这个表达说明两类差异：事实认识不同，或者对相同事实的评价不同。

    \(\hat{\mathbf v}\) 上的帽子表示估计。读错源码、看错版本号，都会使估计偏离实际属性 \(\mathbf v\)。即使一个人按自己的估计和权重得出了自洽的排序，依据仍可能有错，需要由证据纠正。第 2 部分讨论这类问题。

    而在事实认识相同的情况下，权重不同就足以产生不同排序。有人比较 Snap 与 Flatpak 时主要关心 CLI、IDE 打包和上游发布；有人更关心启动时间、桌面集成或打包来源的可审计性。他们需要先核对各项实际表现，再说明自己为什么更在意其中一些属性。

    个人排序由此有了明确的适用条件。把这组条件一并交代，别人才能判断它对自己的选择有什么参考价值。

    1.4 先找到分歧，再决定怎样处理 #

    “更在意什么”只是分歧的一种来源。实际讨论中，还可能存在以下差别：

    争议对象 典型表述 需要弄清什么 处理方式
    必须满足的约束 \(C\) 必须无 root、离线运行或通过合规要求 哪些方案在各自条件下可用 明确约束；必要时按不同场景分别讨论
    属性估计 \(\hat{\mathbf v}\) 这个设计增加维护成本；启动慢约 300 ms 比较条件与依据是否可靠 核对文档、实现和测量
    对未来的预测 Wayland 三年后能否满足某项工作流 判断标准、时间范围和预测依据是什么 记录假设，约定后续观察
    权重 \(\mathbf w\) 我更在意启动时间 对事实的认识接近后，各自仍在意什么 说明取舍，接受个人选择不同

    约束集 \(C\) 用于筛选可行方案。例如，某个必需软件必须可用，就应先作为条件筛选，而不能靠其他优点补偿。明确约束也不要求双方改用同一套条件；有时只是确认他们面对的本来就是两个选择问题。

    我会先核对与当前结论有关的条件和证据，再讨论偏好。一个人说“Snap 启动慢”，另一个人回答“这是你的偏好”，就跳过了启动时间究竟是多少这个可测量的问题。等双方接受同一组测量结果后，一个人仍认为这个等待时间不可接受，另一个人并不介意，才有理由把这部分分歧归到权重上。

    讨论中随时可能有人补充条件、修正测量。只要启动时间还有疑问，就值得继续查。如果争议在于谁得为这次变化多花时间，还要听听承担这项工作的人怎么想。

    1.5 成本由谁承担，也会影响选择 #

    技术方案的收益和代价，可能分别落在用户、维护者、上游、厂商和管理员身上。同样一项更新，对上游是减少维护分支，对用户却可能是适应行为变化。直接把这些影响合成一个“总成本”，需要先说明怎样比较工时、费用、风险和控制权。

    Ubuntu 把 Firefox 从 deb 换成 Snap 是一个具体例子：Mozilla 可以直接发布更新，Ubuntu 维护者减少了跨发行版维护软件包的工作，用户则要适应首次启动性能和 apt 安装结果的变化。1 双方都在面对真实后果，只是获得的收益和承担的工作不同。

    当决策者与成本承担者不是同一批人时，后者还可能缺少参与决定的机会。这时，分歧除了“方案是否有效”，也包括“这项工作为什么由我承担”。

    不过，技术改进也可能同时减少多个参与者的负担。包管理器相对逐个源码编译、容器镜像相对手工配置环境，都可能减少重复工作。因此，既要看成本如何分配，也要看哪些成本确实降低了。

    “X 不好”有时是在表达“不愿承担这项成本”。确认对方的意思以后，讨论就可以落到具体责任：成本来自哪里，由谁承担更合理，在什么条件下能够接受。

    1.6 小结 #

    选择不同，可能来自用途、约束、事实认识、预测或偏好不同。先把分歧定位到其中某一项，才知道需要补充什么：事实问题需要证据，预测需要说明假设，个人取舍可以不同，涉及其他人的成本还要讨论责任。接下来先看证据怎样影响我们对技术的认识。

    2 有限的证据：个人体验能说明什么 #

    2.1 把一次体验放回发生条件 #

    社区排查挂起恢复问题时，经常同时记录驱动和内核版本。同一个用户升级内核或驱动之后，故障可能消失，也可能在后续更新中再次出现。于是，“这台机器无法恢复”还需要附带配置、操作步骤和发生时间，才能与别人的报告比较。

    可以把记录到的条件写成：

    \[ Z = (\text{发行版},\ \text{内核},\ \text{驱动},\ \text{固件},\ \text{OEM},\ \text{硬件型号},\ \text{桌面环境},\ \text{文件系统},\ \text{负载},\ \text{时间},\ \dots) \]

    \(Z\) 表示我们观察和记录到的环境。负载时序、固件内部状态等因素可能没有被完整记录，因此两份看起来相同的配置记录，也可能对应不同的运行条件。复现时需要继续排查这些差别。

    2.2 一次故障能说明什么 #

    假设我的笔记本从挂起状态恢复失败，你照着同样的步骤试了一次，却能正常唤醒。两份报告都值得留。我们可以先对照内核、驱动和日志，看看哪项差异有助于复现故障。即使记录下来的配置完全相同，两次尝试也可能得到不同结果。

    一次经核实的故障，就足以推翻“在这些条件下从来不会出错”。要估计同一条件下的故障概率 \(P(\text{故障}\mid Z=z)\)，还得知道机器是怎么选的、每台试了多少次，其中多少次失败。比较两组配置时，两边的记录都得经得起这样的检查。附录 C.1 给出了相应的概率表达。

    这也是为什么评论区里即使有许多故障报告，我们仍然很难据此判断故障有多普遍。遇到问题的人会来求助，顺利唤醒机器的人可能根本没有发帖。第 4 部分再看这种差别怎样影响我们对整个社区的印象。

    2.3 双方可能在检查不同属性 #

    一个人主要用 Flatpak 安装桌面 GUI 应用，测试过文件选择、屏幕捕获和权限调整；另一个人尝试用它运行 CLI 工具和 IDE，检查的是命令入口和访问宿主工具链的方式。两人的依据都可能可靠，但回答的问题不同。桌面集成的测试结果不能直接代替开发工具的测试，反过来也一样。

    这种差别可以称为证据覆盖范围不同。讨论时，先列出双方已经核查了哪些属性，就能发现哪些结果可以直接比较，哪些还需要补充材料。

    如果用记号表示，\(m_{ik}=1\) 表示第 \(i\) 个人在第 \(k\) 项属性上有原则上可核查的依据，\(m_{ik}=0\) 表示目前没有。它只记录依据是否存在，不决定依据是否正确。“有源码但读错了”和“尚未找到依据”都需要修正认识，只是下一步应做的检查不同。

    2.4 新证据怎样改变选择 #

    假设两个人原本都认为某个方案启动较慢，新测试表明它在目标环境中已经明显改善。这个结果会改变对启动时间的估计。不过，一个很在意启动时间的人可能因此改选，另一个主要受软件兼容性限制的人则可能继续使用原方案。

    先考察用途、约束和权重暂时不变，只更新事实估计的情形。设 \(D^{\text{前}}\) 为原来两个方案的评分差，\(\Delta\) 为新证据引起的差值变化，那么：

    \[ D^{\text{后}} = D^{\text{前}} + \Delta \]

    证据能改变多少评分，取决于它修正了哪些属性、修正幅度有多大，以及这些属性在当前选择中有多重要。排序是否反转，还要看更新后的差值是否越过零。如果原来 \(D^{\text{前}}=0\)，表示两方案在当前评价下并列；证据可能打破并列，这与已有偏好发生反转是两种情况。详细推导见附录 C.2。

    这里比较的是两个方案的差别。如果一条信息改变了对两者的评价，却没有改变它们之间的评分差，排序也可以保持原样。排序不变，因此不能单独证明对方没有接受新信息。

    同一条证据被重复转述，也不会因此变成多份独立观测。在已经理解并纳入它的前提下，没有新增内容的重复转述通常不会继续修正估计；独立的复现实验则可能提供新的信息。讨论中值得追问的是这次发言增加了什么，而不只是同一种说法出现了多少次。

    2.5 共同核查以后，选择仍可能不同 #

    对方提出自己遗漏的属性、提供更准确的测量，或者指出自己读错了源码，都可能改变判断。讨论的直接收益，是让双方更清楚依据是什么、哪些认识需要修正。最终是否选择同一方案，还取决于各自的约束与权重。

    提出问题后，还需要给出证据。“你没有考虑可维护性”提出了一项值得检查的属性，后面还应说明具体是哪部分维护、由谁承担，以及有哪些可核查材料。属性清单可以在讨论中扩展，相关依据则需要继续检查。

    因此，共同核查的范围可以扩大，而结论既可能靠近，也可能保持不同。5.2 节会把这个过程整理成具体做法。

    2.6 依据的数量、质量和重要程度 #

    设想一个选择主要取决于第十项属性：有人对前九项都有可靠认识，却没有核查第十项；另一个人恰好掌握第十项。仅仅比较“了解九项”和“了解一项”，就很难判断谁的依据更能支持当前选择。

    需要一起看的，是依据覆盖了什么、认识是否准确，以及这项属性怎样影响结论。没有依据的人也可能持有很强的估计；找到来源以后，仍要检查来源是否被正确理解。

    专业经验在这里很有用。长期维护 Mesa 的开发者通常能提供更准确的线索，也更容易识别问题出在哪里；具体判断仍可继续通过源码、日志和 issue 核查。这个要求同样适用于我：我核查过 snapd 的沙箱模型，systemd 的其他行为还要分别查证。对于只有二手认识的问题，我仍需补上相应依据。

    2.7 小结 #

    读到相反的报告，我会先看两个人在什么条件下试过什么，再看他们关心的是不是同一项表现。新测试澄清了启动速度，受兼容性限制的人仍可能坚持原来的选择。如果我拿出了测试，对方却开始追问我属于哪个阵营，接下来要判断的就是这段对话还在谈什么。

    3 身份：分歧什么时候不再关于技术 #

    有些争论在补充材料后能够继续：双方发现配置不同，或修正了对实现的理解。另一些争论却会换掉对象：日志贴了，复现步骤给了，上游 issue 引了，回应变成了“你是什么人”。这里关注的是这种变化。

    3.1 技术投入可能成为身份的一部分 #

    一个人花了几百小时配置 Arch，读过 systemd 的文档，也能在邮件列表里回答问题。这些投入提高了他处理问题的能力，并可能帮助他在社群中获得认可。如果技术熟练度与社群归属逐渐联系起来，别人对工具的批评，也可能被他理解为对自己能力或地位的质疑。

    这种联系可以从两个方向形成：投入带来熟练度与归属感，已有的归属感也会影响后来的技术选择和解释方式。在成员缺少长期相互了解的场合，工具选择、术语和内部规则还可能成为识别“内行”的捷径。

    这是一种可能的联系。判断它是否影响了具体争论，需要观察参与者怎样回应材料；投入时间本身只能说明他在这项技术上花过多少精力。

    3.2 敌意怎样在互动中被维持 #

    如果批评被理解为身份威胁，回应就可能变得更有敌意。敌意发言又可能获得更多互动和可见性，让旁观者更容易记住“对面都是这种人”。这个印象进一步强化群体边界，使下一次批评更容易被当作敌意。它可以概括为：

    技术投入与群体认同 → 批评被理解为身份威胁 → 敌意回应 → 冲突获得可见性 → 对另一群体的负面印象增强 → 群体认同进一步强化

    第 4 部分的研究支持其中关于内容可见性的部分。其余连接是本文根据前述现象提出的机制假设，用来解释这些反应可能怎样相互加强，因果关系仍待验证。

    双方还可能把彼此的语气当作自己态度的理由：我认为你先挑衅，你认为我的回应证明了恶意。即使某个技术事实已经澄清，这种对人的解释仍可能继续维持。如果缓和还会被身边的支持者理解为认输，退出敌意互动就会变得更难。

    所以，补充技术证据能否推进对话，还取决于双方是否继续用它检验原来的技术判断。

    3.3 看什么结果能让判断被撤回 #

    对于“这个设计在配置 Z 下容易出问题”，双方可以核查日志和复现步骤，调整对故障原因与发生条件的判断。这里存在能够支持或削弱原解释的材料。

    有些身份标签则使用封闭的解释方式。比如，提出者已经认定对方是“厂商的盲目拥护者”：举证被解释为急着洗地，沉默被解释为被戳穿，认错被解释为被迫让步，语气平和又被解释为掩饰。几种不同回应都被当作同一个结论的证明，对方也就很难通过材料纠正这个判断。

    我会用一个问题检查这种情况：

    什么可观察的结果，会让提出者修改或撤回这个判断？

    “支持某厂商”“长期使用某系统”可以是一个人对自己经历或偏好的描述。问题在于，它是否被用来预先否定对方的论据，以及提出者是否允许自己的解释被事实修正。

    如果任何回应都被解释成同一个标签，继续补充技术材料就很难检验这项指控。这个判断可以帮助决定是否继续对话，见 5.3 节。

    3.4 一句话正在陈述什么 #

    下面几类句子需要不同的回应：

    陈述类型 例子 怎样继续
    事实 snapd 以 GPLv3 发布 核查来源与适用范围
    经验样本 我的笔记本无法休眠 补全环境、步骤和结果
    工程评价 这种设计维护成本太高，不值得采用 先核查成本，再讨论用途、约束和取舍
    偏好 我更喜欢 KDE 了解使用习惯，无须证明别人也应喜欢
    身份判断 真正懂 Linux 的都用 X 检查它是否在用群体归属代替技术依据

    工程评价通常同时包含事实与取舍。“维护成本高”需要说明工作量来自哪里，“不值得采用”还需要说明预期收益和用途。把两部分拆开，才能知道争论是在核查成本，还是在评价是否值得承担。

    讨论中常见的跳跃也可以据此辨认：

    • 由样本推总体：从一次体验，直接概括整项技术的表现。
    • 由偏好推义务：自己愿意折腾系统，便要求其他使用者承担同样的工作。
    • 由评价推身份：回应“这个设计有问题”时，开始判断批评者属于哪类人。
    • 由解释推立场：某人说明设计产生的约束，被理解为他在为某一方辩护。

    “这 API 是垃圾”也需要追问。它可能在表达一次受挫的经验，也可能在概括一组工程代价。先问清是哪项行为、哪种用途和哪些后果，才能决定核查什么；仅凭句式，很难知道说话者希望讨论哪一层。

    3.5 话题换成了人的资格 #

    当对话开始出现下面的回应时，我会留意讨论对象是否已经改变：

    • 用对方所属群体代替对当前论据的检查。
    • 用他人对这个人的评价，直接裁决当前技术命题。
    • 把“你用什么系统”当作结论成立与否的依据。
    • 要求对方先证明立场正确，才回应他提供的材料。

    不过，身份和经验信息也有合理用途。长期维护某个驱动，可以说明判断来自怎样的工作，也有助于追问具体依据。它提供的是核查线索。当前结论仍要看相应的源码、日志、文档或实验，而不能只由说话者的资格决定。

    3.6 小结 #

    技术投入可能影响归属感，对批评的反应也可能因此带上身份意味。当人的标签替代论据，而且这个标签不再接受反证时，技术讨论就很难继续。判断时应看具体回应如何使用证据，而不再凭群体归属猜测动机。

    4 可见性：为什么少数冲突会变成我们眼中的“整个社区” #

    假设一篇文章有几千人读过，留下几十条评论。只看评论区，我们对“大家都在说什么”的印象就来自这些发言；没有评论的人怎样看这个话题，仍然不知道。观察整个社区时，需要把这个缺口算进去。

    4.1 从持有观点，到发言，再到被看见 #

    一种观点进入视野，至少经过两次筛选：持有它的人是否愿意发言，已经发表的内容又是否被我们看到。遇到故障的人可能更愿意求助，容易引起回应的发言又可能获得更多展示。这样形成的评论区，与全部用户的经历分布就可能不同。

    在固定的问题、人群和时间范围内，用 \(o\) 表示一种回答，\(P_{\text{pop}}(o)\) 表示它在成员中的比例。先把每人的参与简化为一次表达机会，可见分布可以写成：

    \[ P_{\text{obs}}(o) \propto P_{\text{pop}}(o) \cdot s(o) \cdot r(o) \]

    其中，\(s(o)\) 是持有这种回答的人发言的概率，\(r(o)\) 是发言以后被看到的概率。某种回答越容易被说出、越容易被展示，它在可见内容中的比例就越可能高于在成员中的比例。

    这个式子只描述一轮筛选。一个人反复发帖、内容被多次转发，以及可见内容反过来影响下一轮表达，都需要进一步考虑，见附录 C.3。用于技术故障讨论时，还应按第 2 部分的环境条件 \(Z\) 区分报告，以免把不同配置下的结果混在一起。

    关于鸿蒙 PC 的争议给了我一个具体观察：支持与反对两侧都有人使用标签回应技术问题，旁观者也容易据此形成“对面全是这种人”的印象。这个观察能说明一种讨论形态；要判断两侧分别有多少人这样表达，还需要知道没有进入视野的成员是什么样。

    4.2 谁进入了样本，以及样本是否彼此独立 #

    选择偏差问的是谁更容易进入样本。机器正常的人可能没有发帖的动机，遇到故障的人则可能专门来求助。因此，随机询问一百位用户，与收集一百条故障帖子，回答的并不是同一个问题。

    筛选也可能发生在观察者一侧。长期关注某个平台的人，会记住批评者受到攻击的案例；关注其他品牌争议的人，也会记住另一批相似事件。这些事件可以都是真的，但只从自己熟悉的话题取样，仍不足以比较不同群体中这类行为的比例。

    样本相关问的是已有观察之间共享了多少来源。一百条看过同一视频以后发表的相似评论，可能受到相同内容、传播链和社群环境影响。若忽略这些共同来源，直接按独立观测统计，就可能高估其中包含的独立信息，低估推断的不确定性。

    两者可以同时出现。增加评论数量，有助于观察更多表达，但不能自动补上缺失的人群和共同来源。要估计故障发生率，还需要说明总共有多少用户或尝试、怎样选取样本，以及哪些条件可能影响结果。

    所以，“评论区里全是抱怨”首先描述的是可见样本。它可能来自总体故障较多，也可能来自故障用户更愿意发言、抱怨更容易被展示，或几种机制共同作用。仅凭评论区，通常无法分清各自贡献了多少。

    4.3 研究分别支持了哪些判断 #

    关于表达与可见性，可以把两类研究放在一起读：一类观察技术协作中发生了什么，另一类实验改变内容排序，观察用户接触到什么。它们回答不同问题，提供的证据也不同。

    Sarker、Turzo 与 Bosu 分析了 2828 个 GitHub 项目、约 1.015 亿条 pull request 评论，并对自动分类结果抽样进行人工校验。研究记录了辱骂性语言、引战和侮辱等表达，也发现它们与项目热度、问题解决率和参与者过往行为存在统计关联。2 这项研究系统记录了开源协作中的不友好表达；关联的因果方向及其在其他技术社区中的适用性，还需要分别研究。抽样、分类校验和回归结果的细节保留在脚注中。

    Brady、Doyle、Elnakouri 等人的 Bluesky 实验则改变了用户看到内容的方式。研究将 2000 名美国两党活跃用户随机分入三种排序，在跨越 2024 年大选的八周里观察结果。相对逆时序排序，互动优先排序增加了群体间敌意、道德化、情绪化和毒性政治内容的暴露；研究者设计的替代排序则比互动优先排序减少了这类内容的暴露，整体平台享受度保持相当。3

    研究在实验期间所测的指标中，没有检出参与者自身发帖、点赞和转发行为的显著变化；其他行为变化仍需另行检验。“用户看到什么”和“用户自己怎样行动”需要分别测量。

    Twitter 的算法审计也发现互动排序会放大情绪化和外群体敌意内容，同时提醒替代排序也可能增加同立场内容。4 Facebook 与 Instagram 的三个月实验则没有检出所测关键政治态度的显著变化。5 研究内容暴露怎样影响态度与行为，需要分别取得各环节的证据。

    对技术社区本身，Miller 等人对 100 条毒性讨论的定性分析补充了“这些表达怎样出现”的材料，但其抽样不用于估计普遍程度。6 因此，本文据研究作出的判断是：已有表达与分发方式都值得考察；它们并未给出技术社区中发言意愿 \(s\) 和可见性 \(r\) 的一组现成参数。

    观察者对内容的理解也会引入偏差。2023 年研究发现，观察者往往高估发帖者自报的道德愤怒；Bluesky 研究又发现，用户低估了其他人认为毒性帖不恰当的程度。3 前者涉及对作者情绪的推断，后者涉及对旁观者态度的估计。这是阅读内容之后的解释问题，与“哪些内容进入视野”有所区别，却同样会影响我们对群体的印象。

    4.4 讨论环境怎样改变体验 #

    邮件列表、GitHub issue、论坛和视频评论区给人的体验差别很大。除了参与者本身，交流方式也会影响谁愿意发言、什么内容容易留下来：

    • 规模与重复相遇：二十人的长期邮件列表，与二十万人的公共论坛，成员反复遇见彼此的机会不同。
    • 声誉能否累积：固定用户名和可追溯的历史，能让后续参与者了解此前的发言；临时账号和一次性参与会削弱这种连续性。
    • 上下文是否连贯：长期讨论可以引用已经确认的前提；推荐流不断带入新参与者时，前情往往需要重新解释。
    • 发现内容的方式：按时间、按热度或依赖推荐，影响哪些发言更容易被看到。
    • 管理与规范：行为准则是否明确，执行是否持续，会影响参与者对回应后果的预期。
    • 发言的社会成本：实名、半实名与匿名，使发言与现实关系的联系程度不同。
    • 社群边界：内部讨论被推向更大人群以后，参与者构成和彼此了解的程度也会变化。

    这些条件会与成员构成共同影响讨论。分析一次交流经历时，可以先检查这些条件，再考虑其中哪些现象可能出现在更大的群体中。

    在我观察到的鸿蒙 PC 争议中，不少讨论发生在推荐流主导的平台上，一次性参与者较多，上下文也不连续。换成长期交流的邮件列表后，需要重新观察发言方式和传播条件；现有案例不足以预言同一批人会怎样回应。

    4.5 检查自己看见了什么 #

    形成“某个社区就是这样”的印象时，我会先检查它来自哪些渠道：看到了多少不同来源，是否反复看到同一场冲突，哪些成员始终没有进入视野。

    4.6 小结 #

    评论区记录了已经说出、又被看到的内容。发言意愿、分发方式、样本之间的共同来源，以及观察者怎样理解这些话，都会影响最终印象。研究可以分别检验这些过程，但由局部观察推断整个群体时，仍需要清楚的人群范围、取样方式和分母。

    5 参与而不被消耗 #

    前面的分析最终要帮助我决定怎样参与：哪些分歧值得继续核查，哪些需要承认条件不同，哪些已经换成了无法回应的身份指控。实际使用时，可以按下面的问题寻找分歧所在。

    检查什么 可以问什么 下一步
    当前问题 我们在比较事实，还是在选择方案？ 先说明各自希望回答的问题
    可行条件 必需软件、权限或部署条件是否不同？ 列出约束，必要时按各自场景讨论
    运行环境 两份报告的配置和步骤是否可比？ 对照版本、硬件、操作步骤与日志
    依据覆盖 双方检查的是同一项属性吗？ 补充尚未讨论的相关属性和材料
    事实估计 对同一属性的认识为什么不同？ 核查文档、源码、测量和解释
    未来预测 预测依赖什么假设，何时能够检验？ 说明不确定性和后续观察标准
    个人取舍 接受同一组事实后，各自仍在意什么？ 说明权重与愿意承担的成本
    对话对象 回应仍在检查论据，还是只在判定人的资格？ 尝试回到命题；无法继续时停止投入

    这张表用于定位问题。比较技术事实时，重点是条件和依据；决定采用哪个方案时，再结合约束与偏好。若对话已经只剩资格指控，也可以直接结束，无须先完成表里的全部检查。

    5.1 把适用条件写进结论 #

    “Arch 更好”省去了评价所依赖的条件，读者只能用自己的需求理解。写成“在重视软件新鲜度、愿意承担维护责任的条件下，Arch 更合适”，就能说明结论适用于谁。即使读者不接受这组取舍，也知道哪些属性值得按自己的情况重新比较。

    回应或报告故障时，可以把想问的内容写具体：

    • 对方报告故障：说明自己尚未复现，再询问内核、驱动、硬件、步骤和日志。
    • 对方报告正常体验：给出自己能够复现的配置，请对方帮助比较差别。
    • 自己报告故障：说明在什么环境下执行了什么操作、出现什么结果，并附上可核查材料。

    这些信息会把一次体验变成可以继续排查的问题，也让别人知道结论的适用范围。

    5.2 补充自己尚未核查的依据 #

    如果分歧来自双方检查的属性不同，可以先请对方说明遗漏了什么，再看有什么材料能帮助核查。我也可以提供自己的来源和复现条件，让对方检查。

    这个过程包括三个动作：先确认新提出的属性与当前问题有关，再核查具体依据，最后判断它怎样影响原结论。双方可以在不同环节补充材料，也可能各自修正一部分认识。

    新信息能否改变当前排序，还受用途和权重影响。不过，交流的价值也包括解释一个暂时用不到的属性、修正未来会用到的认识，或者帮助对方完成学习。这些收益很难只用“是否改变了选择”衡量。直接影响评分的数学条件放在附录 C.2。

    决定是否投入时，我会问：

    • 这份信息可能修正什么认识？
    • 依据能否核查？
    • 我是否愿意重新检查自己的判断？
    • 继续交流需要多少时间？

    这些问题帮助估计交流可能带来的收益，也保留了选择不继续的余地。一方已经掌握较多相关知识时，交流还可能主要成为单向讲解。在我看来，这类工作很值得投入；只是时间投入不对称，开始时说明期待会更合适。

    5.3 判断回应是否还在处理原问题 #

    回到开头那场关于 Snap 的争论。对方把批评收窄到 Store 以后，我愿意接着听他对商店的具体意见。如果他追问我和 Canonical 的关系，我会看接下来的回应里，还有没有哪一条材料值得一起查。

    语气重的人也可能贴出日志，指出我漏掉了一个条件。即便有人断言“所有配置都不会出错”，我也知道可以拿什么反例同他讨论。反过来，一个人完全可以措辞客气，却接连几次绕开我给的材料，只问我为什么替谁说话。到了这一步，我会停下来。以后有了新问题或新证据，还可以再谈。

    可见性会影响我对社区的印象，因此选择输入源时，我会先看自己希望得到什么：

    5.5 留下一份可核查的记录 #

    公开讨论还有旁观者和后来的读者。有些人只阅读，不发言；有些人会在几个月后遇到相似问题。因此，即使对话双方没有改变选择，整理来源、配置、论证和反例仍然有用。

    我能够负责的是把这份记录写清楚，让读者检查与自己有关的部分，也让后续反馈有机会修正其中的错误。它比要求每个对话者当场承认结论，更接近我愿意持续投入的工作。

    5.6 小结 #

    我会先确认问题，再核查条件和依据，最后说明取舍。能补充信息的分歧值得继续，清楚的偏好差异可以接受，持续回避命题的对话则可以结束。停止某次交流不等于证明对方错误；出现新材料或新问题时，也仍可重新讨论。

    结语：把讨论留在具体问题上 #

    技术争论中有大量值得核查的分歧。双方可能需要补充事实，也可能在事实对齐后仍有不同取舍；先分清争议属于哪一种，才知道怎样继续。

    长期使用和学习一个系统，会形成经验与偏好；当这些经验被用来裁决谁有资格发言，或者个人愿意承担的成本被改写成别人的义务，讨论就很难继续围绕原问题展开。

    个人体验需要附带发生条件，工程评价需要说明用途和代价，解释一项设计为何存在也可以与批评它的实现同时进行。有人愿意维护 Arch，有人希望 Debian Stable 的行为更可预测；同一个人也可以喜欢 Windows 的开发工具，同时批评它的某些设计。这些判断能够具体讨论，无须先把人分进阵营。

    质疑可以落在具体依据上：“这个结论的依据是什么？我在这组条件下测到的结果不同。”这样既指出了分歧，也给出了对方能够回应的问题。

    获取技术评价时，也要检查材料如何进入自己的视野。反复主动搜索负面评论，会在已经筛选过的发言中再次挑选同一方向的材料。这样的印象可以成为调查具体问题的线索；评价技术表现和用户态度，还需要比较不同来源与使用条件。

    我希望一次讨论结束以后，双方更清楚哪些事实已经核查、哪些认识仍不确定，以及选择为何不同。结论可能改变，也可能不变；只要我们对问题的理解比开始时更准确，讨论就有值得保留的成果。

    附录 A：检查自己是否采用了同一标准 #

    对称性检查可以用来检查自己的举证标准：在相关条件和证据质量相当时，如果换成自己更喜欢或更不喜欢的对象，是否还会接受同一种推断？

    例如，面对一条批评 Snap 的故障报告，我要求版本、配置、复现步骤和日志；面对一条批评 Flatpak 的报告，也应考虑相同的信息。若仅因更喜欢其中一个，就对一侧要求完整复现、对另一侧接受一句抱怨，需要重新检查自己的标准。

    这里比较的是怎样使用证据。技术对象本身的差异仍然要保留：默认项和可选项、安装规模、迁移成本和维护责任不同，都可能支持不同评价。直接对调 Windows 与 Linux 的名字，可能会改变原有技术事实；检查偏见时，应比较在相关条件相当时是否采用了同一标准。

    同样，把“必须接受更新”改说成“能持续获得更新”，是在改变对同一行为的评价角度；它可以帮助发现取舍，却没有完成举证标准的对称性检查。两项检查分别有用，不能互相替代。

    附录 C：数学表达及其适用范围 #

    这些表达用于检查推理关系，赋值需要满足各自的前提并取得相应数据。日常讨论可以借用这些关系，无须逐项计算。

    C.1 一次观察与条件概率 #

    用 \(Y=1\) 表示发生故障，\(Y=0\) 表示没有发生。在记录到的条件 \(Z=z\) 下，可以写成：

    \[ Y\mid Z=z\sim\operatorname{Bernoulli}(p(z)),\qquad p(z)=P(Y=1\mid Z=z) \]

    两个人分别使用 \(z_A\) 和 \(z_B\)，于是可能对应不同的条件概率 \(p(z_A)\) 和 \(p(z_B)\)。但即使两个概率相同，也可能观察到一次成功和一次失败。观察值不同，不足以单独证明条件概率不同。

    一个经核实的故障案例，可以反驳覆盖其条件的“从不发生”判断。若要进一步比较发生率，则需要观测次数、取样方式和可比条件。使用似然比讨论一项观察有多大区分力，也需要先说明正在比较哪些假设，以及各假设给出的结果概率；一个案例本身并不提供这些概率。

    C.2 证据更新与排序变化 #

    固定约束、属性集合和权重，设两个方案在第 \(k\) 项属性上的估计差值为：

    \[ \hat\delta_{ik}=\hat v_{ik}(x)-\hat v_{ik}(y) \]

    \(S_E\) 表示本次证据 \(E\) 更新到的属性集合，撇号表示更新后的估计。若其他属性的估计不变，则：

    \[ \begin{aligned} D^{\text{前}} &= U_i(x)-U_i(y)=\sum_k w_{ik}\hat\delta_{ik} \\ \Delta &= \sum_{k\in S_E}w_{ik}\big(\hat\delta'_{ik}-\hat\delta_{ik}\big) \\ D^{\text{后}} &= D^{\text{前}}+\Delta \end{aligned} \]

    对于 \(D^{\text{前}}\ne0\) 的情况，严格翻转排序要求：

    \[ D^{\text{前}}D^{\text{后}}<0 \quad\Longleftrightarrow\quad D^{\text{前}}\Delta<0 \quad\text{且}\quad |\Delta|>|D^{\text{前}}| \]

    也就是变化方向与原来的评分差相反，并且变化量足以越过零。若更新后恰好为零，两方案变成并列；若原来为零，则更新可能打破并列。评分并列本身不表示这个人没有认识或没有意见。

    这里还可以区分两个集合：

    \[ K_j=\{k:m_{jk}=1\},\qquad W_i=\{k:w_{ik}\ne0\} \]

    \(K_j\) 记录对方在哪些属性上有可核查依据，\(W_i\) 记录自己当前赋予非零权重的属性。真正进入评分更新的是 \(S_E\)。若 \(S_E\cap W_i=\varnothing\)，则 \(\Delta=0\)；交集非空时，仍要看更新幅度、方向以及不同项是否相互抵消。

    只有在这次证据的影响局限于 \(K_j\)、即 \(S_E\subseteq K_j\) 的前提下，\(K_j\cap W_i\ne\varnothing\) 才是评分差可能改变的必要条件。证据也可能通过关联推断影响其他属性，或者促使人重新考虑约束与权重；这些情形要另外处理。因此，这个交集不能单独决定一场交流是否值得投入。

    C.3 可见样本怎样形成 #

    4.1 节先把每人的参与简化为一次表达机会，并固定讨论问题、人群与时间范围。令 \(o\) 表示一种回答，\(s(o)\) 表示持有该回答时发言的概率，\(r(o)\) 表示已经发言后被观察到的概率。可见分布是归一化后的：

    \[ P_{\text{obs}}(o)= \frac{P_{\text{pop}}(o)s(o)r(o)} {\sum_{o'}P_{\text{pop}}(o')s(o')r(o')} \]

    这里假定分母非零。仅观察 \(P_{\text{obs}}\)，通常无法分别还原总体分布、发言意愿与可见性；不同的组合可能产生相同的可见结果。

    如果按帖子而不是按成员统计，还需考虑同一人多次发言的频率。连续多轮讨论中，可见内容也可能改变后续观点和表达方式，不能再把这个单轮表达直接当作完整的动态模型。技术故障报告还应考虑环境条件 \(Z\)，以免把配置差异和发言选择混为一项影响。

    C.4 区分能力与互信息 #

    用 \(\Theta\) 表示当前命题可能的取值，用 \(E\) 表示可能收到的证据。给定两者的联合分布，互信息可以写作：

    \[ I(\Theta;E)=H(\Theta)-H(\Theta\mid E)\ge0 \]

    \(H\) 表示熵，用来描述分布中的不确定性。互信息衡量的是：在各种可能的证据上取平均后，知道 \(E\) 能减少多少关于 \(\Theta\) 的不确定性。某条具体消息可能揭示新的解释，使人暂时更不确定，这与平均意义上的非负性并不冲突。

    使用这个公式，需要先明确命题与概率模型。一句身份标签提供的信息不足以计算互信息；评价一段对话的价值还要结合它具体增加了什么。正文 5.3 节采用的是可观察的判断：新回应有没有增加能够核查、比较或继续追问的内容，以及继续交流的成本是否值得。

    C.5 这些记号如何配合 #

    前面的关系可以概括为两条相交的过程：

    \[ \begin{aligned} P_{\text{pop}},\ s,\ r &\longrightarrow P_{\text{obs}} \longrightarrow \text{更可能接触到的 }E \\ C &\longrightarrow \text{可行方案} \\ Z,\ E &\longrightarrow \hat{\mathbf v}_i\text{ 的形成与更新} \\ \hat{\mathbf v}_i,\ \mathbf w_i &\longrightarrow U_i \longrightarrow D^{\text{前}},\ D^{\text{后}} \end{aligned} \]

    一条过程说明材料怎样进入视野，另一条说明人在约束下怎样根据认识和偏好作出选择。\(m\) 记录哪些属性已有可核查依据，帮助定位需要继续检查的地方；它不直接进入评分公式。这里的箭头表示分析上的联系，并不宣称这些关系已经被统一估计为一个经验模型。
